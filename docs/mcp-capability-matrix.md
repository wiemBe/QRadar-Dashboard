## 1. Findings that shape our architecture

### 1.1 QRadar uses `POST` for updates, so "POST" ≠ "create"

`update_offense`, `update_qid_record` and `update_dsm_event_mapping` are all `POST`.
There is no `PUT`/`PATCH` anywhere in the codebase. Any verb-level policy must treat
`POST` as *mutating*, full stop.

### 1.2 Disabling `POST` also disables Ariel search execution — and that is correct for us

`create_ariel_search` (`POST ariel/searches`) and `validate_aql` (`POST ariel/validators/aql`)
are `POST` tools. A GET-only MCP policy therefore removes the ability to **run AQL through MCP
at all**.

This is not a limitation to work around — it independently confirms the architectural rule:

> Direct QRadar REST/Ariel APIs own deterministic background collection and scheduled AQL
> execution. MCP is restricted to inventory retrieval and future AI-agent investigations.

Ariel search execution is stateful (create → poll status → fetch results → delete). Driving that
through an LLM-facing tool surface would be both non-deterministic and needlessly write-capable.
Our `QRadarRestProvider` owns it; our `QRadarMCPProvider` never touches it.

### 1.3 Upstream ships insecure defaults

| Upstream default | File | Risk | Our override |
|---|---|---|---|
| `verify_ssl: false` | `config.example.json` | TLS interception of a privileged SIEM token | `verify_ssl: true`, mounted CA bundle |
| `"debug": true` | `config.example.json` | Verbose error/stack disclosure | `debug: false` |
| `GET/POST/DELETE` all `true` | `feature_toggles.json` | Full CRUD incl. reference-set and offense writes | `POST: false`, `DELETE: false` |
| `uvicorn.run(app, host="0.0.0.0", port=5000)` | `server.py:349` | Binds all interfaces | never publish the port; internal Docker network only |
| Upstream compose maps `5001:5000` | `docker-compose.yml` | Reachable from host | our compose publishes **no** ports for MCP |

We change none of this *in* the repo. All of it is overridden by **mounted configuration**
(`config.json`, `feature_toggles.json`) — see §4.

### 1.4 `approval_required` is not a security control

`approval_required` defaults to `True` in `tools/base.py:145`, GET tools override it to `False`,
and only the four `data_classification` writes set it explicitly. The `reference_data`, `offense`
and `ariel` write tools inherit the default. It is an **interactive client-side prompt hint** —
an autonomous agent can simply not honour it. Our enforcement is the verb toggle plus network
isolation, never this flag.

### 1.5 Packaging detail

The directory is `qradar-mcp` but the Python package imports as `qradar_mcp.*`. The upstream
`Dockerfile` handles this by copying into `/opt/app-root/qradar-mcp` and setting
`PYTHONPATH=/opt/app-root/qradar-mcp`. We reuse their Dockerfile unmodified rather than
re-deriving the layout.

## 4. Enforced configuration

Mounted read-only over the container's paths. **No upstream file is edited.**

```jsonc
// deploy/mcp/feature_toggles.json
{
  "verb_toggles":  { "GET": true, "POST": false, "DELETE": false },
  "group_toggles": {
    "log_source": true, "analytics": true, "offense": true,
    "system": true, "config": true, "data_classification": true,
    "asset": true, "ariel": true, "reference_data": true,
    "services": false, "forensics": false, "qvm": false
  },
  "per_tool_toggles": {},
  "resource_toggles": { "aql_events_fields": true, "aql_flows_fields": true,
                        "aql_functions": true, "aql_generation_guide": true }
}
```

Defence in depth, because a toggle file is one bad mount away from being ignored:

1. **Verb toggles** — `POST`/`DELETE` off (enforced in `utils/feature_toggle_manager.py:148`).
2. **Group toggles** — unlicensed/unused groups off, shrinking the surface further.
3. **Network isolation** — MCP sits on an internal Compose network with **no published ports**.
4. **Read-only QRadar service account** — the authorized service token itself carries only
   view capabilities, so a write attempt fails at QRadar even if every layer above is bypassed.
5. **Provider-level allowlist** — `QRadarMCPProvider` refuses to invoke any tool not on a
   hardcoded read-only allowlist, independent of what the server advertises.

Layers 4 and 5 are the ones that actually hold. 1–3 are configuration and can be misconfigured.

## 5. Verification

Regenerate this matrix after any version bump:

```bash
python backend/scripts/extract_mcp_capabilities.py --repo qradar-mcp --check docs/mcp-capability-matrix.md
```

CI fails if the pinned commit exposes a tool absent from this document — a new write tool can
never land silently.
